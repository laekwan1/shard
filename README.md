# Shard · Veil

두 개의 독립적인 Windows 트레이 프로그램입니다.

실제 갈림길은 "우회냐 익명성이냐"가 아니라 **제3자를 거치느냐 아니냐**입니다. 그 하나의 선택에서 나머지가 전부 따라옵니다.

| | Shard | Veil |
|---|---|---|
| 방식 | 나가는 패킷을 커널에서 변조 | 트래픽 전체를 터널로 우회 |
| 제3자 | **없음** | 서버 하나를 거침 |
| 얻는 것 | 우회 | 우회 **와** 은폐 |
| 속도 비용 | 사실상 0 | 프로토콜에 따라 5~99% |
| 필요한 것 | 없음 | 서버, 그리고 그 서버에 대한 신뢰 |

Veil이 은폐만 하는 도구가 아니라는 점이 중요합니다. **터널은 본질적으로 둘을 동시에 합니다** — 트래픽을 남을 거쳐 보내면 우리 ISP는 목적지를 못 보고(우회), 사이트는 우리 주소를 못 봅니다(은폐). 별개 기능이 아니라 같은 원리의 두 결과입니다.

반대로 **Shard의 익명성은 0입니다.** 주소를 전혀 바꾸지 않습니다. 가리는 것은 핸드셰이크 안의 호스트명 하나뿐이고, 목적지 IP는 양쪽에 그대로 보입니다.

### 누가 무엇을 보는가

터널은 흔적을 **지우지 않습니다.** 누가 무엇을 볼 수 있는지를 옮길 뿐입니다.

| 관찰자 | 아무것도 안 씀 | Shard | Veil (내 VPS) | Veil (Tor) |
|---|---|---|---|---|
| 우리 ISP | 목적지 IP + 호스트명 | 목적지 IP (이름은 못 읽음) | 서버 X로 가는 암호화 트래픽 | 브리지로 가는 암호화 트래픽 |
| 접속한 사이트 | 내 IP | **내 IP 그대로** | VPS의 IP | exit 릴레이 IP |
| 서버 운영자 | — | — | **나 자신 — 전부 봄** | 어느 릴레이도 양끝을 모름 |
| 영장이 나오면 | ISP 로그 | ISP 로그 | ISP + VPS 가입·결제 기록 | 구조적으로 어려움 |

세 번째 줄이 핵심입니다. 자체 VPS를 쓰면 우리 ISP는 아무것도 못 보게 되지만, 그 서버는 **내 명의로 내 카드로 빌린 것이고 나 혼자 씁니다.** 익명성 관점에서는 흔적이 사라진 게 아니라 더 선명한 증거가 하나 생긴 것에 가깝습니다. 신뢰가 아니라 구조로 익명성이 보장되는 것은 Tor뿐입니다.

### 그래서 무엇을 쓰나

목적이 "막힌 사이트 보기"뿐이라면 **Shard로 충분합니다.** 서버도 돈도 신뢰도 필요 없습니다. 차단을 뚫는 데 익명성까지 살 이유는 없습니다.

Veil이 필요한 경우는 둘입니다 — 사이트에 집 IP를 보이고 싶지 않을 때, 또는 Shard로 뚫리지 않는 차단을 만났을 때.

## 빌드

필요 조건: Rust(MSVC 툴체인), Visual Studio Build Tools, Windows 10/11 x64.

```bash
cargo build --release
```

`target/release/`에 `shard.exe`, `veil.exe`와 함께 필요한 벤더 바이너리(WinDivert, sing-box, wintun, tor)가 자동으로 배치됩니다. 폴더째 옮겨도 그대로 동작합니다.

두 프로그램 모두 **관리자 권한이 필요**하고(매니페스트에 박혀 있어 실행 시 UAC가 뜹니다), 시작하면 창 없이 트레이에만 올라옵니다. 트레이 아이콘 좌클릭으로 창을 열고, 우클릭 메뉴나 전역 단축키(`Ctrl+Shift+S` / `Ctrl+Shift+V`)로 켜고 끕니다. 창을 닫아도 종료되지 않고 트레이로 내려갑니다.

```bash
cargo test
```

## Shard — 로컬 DPI/SNI 우회

WinDivert로 나가는 패킷을 가로채, 연결을 여는 첫 데이터 세그먼트만 손봅니다. 검열 장비가 그 안에서 호스트명을 읽지 못하게 만든 뒤 원래 목적지로 그대로 보냅니다. 터널도 없고 홉도 늘지 않기 때문에 대역폭 손실이 없습니다.

호스트명이 실린 패킷은 연결당 한 개뿐이므로, 연결이 맺힌 뒤의 트래픽은 파싱만 거치고 그대로 흘러갑니다. **이것이 속도를 잃지 않는 이유입니다.**

### 노브별 trade-off

| 노브 | 낮게/끄면 | 높게/켜면 |
|---|---|---|
| **우회 방식** | 없음 = 비용 0, 우회 0 | 디코이+역순 분할 = 가장 강하지만 연결당 패킷 3~4개 추가 |
| **디코이 반복** | 1회 = 최소 | 3~5회 = 샘플링만 하는 장비에 유효, 패킷 그만큼 증가 |
| **분할 위치** | 레코드 헤더 = 단순 | 호스트명 중앙 = 어느 조각에도 전체 문자열이 안 남음 (기본값) |
| **추가 분할** | 0 = 조각 2개 | 4 = 재조립형 DPI에 강해지지만 패킷 5개 |
| **디코이 무력화** | 체크섬 = 거리 무관, NIC 오프로드가 되돌릴 수 있음 | TTL = 가장 확실, 홉 수 측정 필요 |
| **홉 자동 측정** | 고정 TTL = 즉시 | 자동 = 첫 연결에 SYN-ACK 관측 필요, 거리와 무관하게 정확 |
| **적용 범위** | 지정 도메인만 = CPU 최소, 부작용 0 | 전체 = 목록 관리 불필요, 분할에 예민한 사이트가 깨질 수 있음 |
| **QUIC** | 통과 = 가장 빠름 | 차단 = TCP로 폴백되어 위 전략이 적용됨, 첫 연결에 100~300ms 추가. 호스트명을 읽으므로 지정 도메인에만 적용됩니다 |

요약하면 **Shard가 잃는 것은 속도가 아니라 안정성**입니다. 부작용이 나면 예외 도메인에 넣으세요.

### 자동 학습 — 켜는 것으로 끝

어떤 desync가 통하는지 추측하는 게 실제로 막히는 지점이라, 그 부분을 사람이 하지 않게 만들었습니다.

엔진이 인바운드를 관찰하며 차단의 두 가지 모습을 감지합니다.

| 신호 | 판정 근거 | 비용 |
|---|---|---|
| **리셋 주입** | 우리가 처리한 연결에 핸드셰이크 직후 RST가 도착 (응답을 받은 뒤의 RST는 정상 종료로 무시) | 사실상 0 |
| **무응답** | 핸드셰이크를 보냈는데 8초간 아무 응답 없음 | 인바운드 데이터 패킷 관찰 필요, CPU 몇 % (끌 수 있음) |

같은 호스트에서 실패가 기준 횟수 쌓이면 백그라운드 학습이 돌아, 전략 사다리를 **비용이 싼 순서로** 올라가며 실제 핸드셰이크를 시도하고 처음 성공한 조합을 그 도메인 전용으로 저장합니다. 먼저 통과하는 것을 채택하므로 상시 오버헤드가 "실제로 통하는 최소값"으로 유지됩니다.

설계상 챙긴 것들:

- 탐색 중인 호스트의 실패는 **증거로 세지 않습니다.** 안 그러면 탐색이 탐색을 부릅니다
- 재탐색 쿨다운이 있어, 통하는 전략이 없는 호스트를 무한히 재시도하지 않습니다
- 탐색이 먼저 "우회 없이도 되는가"를 확인하므로 오탐이 나도 멀쩡한 사이트에 전략이 붙지 않습니다
- 오래된 실패 기록은 만료됩니다. 한 시간 전에 실패했다가 지금 되는 사이트를 근거 삼아 탐색하지 않습니다

수동 탐색도 그대로 남아 있습니다.

### DNS

핸드셰이크에서 호스트명을 못 읽어도 그 직전의 평문 DNS 조회로 다 드러납니다. Shard는 `127.0.0.1:53`에 로컬 리스너를 띄워 DoH로 중계합니다(질의는 바이트 그대로 전달 — RFC 8484가 같은 와이어 포맷을 씁니다). 업스트림 주소는 부트스트랩 IP로 고정해, 대체하려는 바로 그 DNS에 의존하지 않도록 했습니다.

응답을 관찰해 만든 IP↔도메인 맵은 호스트명을 읽을 수 없는 연결에 도메인 단위 정책을 적용하는 데 쓰입니다.

### QUIC의 호스트명도 읽습니다

QUIC의 첫 패킷은 암호화되어 있지만, **그 키는 같은 패킷 헤더에 평문으로 적힌 연결 ID에서 유도됩니다.** 설계상 그렇습니다 — 중간 장비가 핸드셰이크를 *바꾸지* 못하게 하려는 것이지 *숨기려는* 것이 아니기 때문입니다. 그래서 패킷을 본 사람은 누구나 키를 만들 수 있고, Shard도 만듭니다.

덕분에 QUIC 연결도 TCP와 똑같이 도메인 단위로 판단합니다. 이전에는 두 가지 선택뿐이었습니다 — 전부 통과시켜 정책을 포기하거나, 차단해서 브라우저를 TCP로 되돌리고 **첫 연결마다 100~300ms를 버리거나.** 이제 그럴 필요가 없습니다.

주소 맵은 폴백으로 남습니다. 재개된 연결이나 ClientHello가 여러 데이터그램에 걸친 경우처럼 열 수 없는 패킷이 있기 때문입니다.

구현은 RFC 9001 §5.2의 키 유도, 헤더 보호 해제, AES-128-GCM 복호화, CRYPTO 프레임 재조립이고 QUIC v1·v2를 모두 다룹니다. RFC 9001 부록 A.1의 공식 키 값과 대조하는 테스트가 있어, 규격에서 어긋나면 바로 드러납니다.

## Veil — 터널 · 익명성

sing-box 코어와 tor 데몬을 관리합니다.

### 프로토콜별 특성

| 프로토콜 | 처리량 | 버티는 한계 | 깨지는 지점 |
|---|---|---|---|
| VLESS + REALITY | 85~95% | 능동 프로빙 | 프로빙하면 진짜 유명 사이트로 연결됨. 서버 IP 평판과 볼륨만 남음 |
| Hysteria2 | 90~130% | 지문 | QUIC 자체가 소수라 튐. UDP 전면 차단 시 사망 |
| Trojan / VLESS | 85~95% | 지문 | 능동 프로빙에 응답 패턴으로 노출 |
| Shadowsocks | 90% | 지문 | 능동 프로빙에 가장 취약 |
| Tor (+브리지) | 1~10 Mbps | 능동 프로빙 | 3홉 지연, exit 차단·캡차 |

Hysteria2가 100%를 넘을 수 있는 것은 brutal 혼잡 제어가 대역폭을 강제로 밀어붙이기 때문입니다. 손실률 높은 회선에서는 직결보다 빠를 수 있지만, 공용망에서는 비매너입니다. 대역폭 값을 정직하게 넣으세요.

### 서버 추가

프로필 탭에 공유 링크를 붙여넣으면 됩니다. `vless://`, `trojan://`, `ss://`(SIP002·레거시·평문 3형식), `hysteria2://`, `hy2://`를 지원하고, 여러 줄이나 base64 구독 본문도 그대로 받습니다. 한 줄이 깨져도 나머지는 살립니다.

VPS가 없다면:

```bash
sudo bash scripts/provision-reality.sh
```

Debian/Ubuntu에 REALITY 서버를 세우고 Veil에 붙여넣을 링크를 출력합니다.

### 누수 차단

- **킬 스위치** — 방화벽 기본 아웃바운드를 Block으로 바꾸고 코어 프로세스와 터널 어댑터만 예외로 둡니다. 터널이 죽은 뒤 사용자가 알아차리기 전까지가 실제 주소가 새는 구간이라 기본값이 켜짐입니다.
- **비정상 종료 시 차단 유지** — 코어가 스스로 죽으면 킬 스위치를 **일부러 내리지 않습니다**. 그게 킬 스위치의 존재 이유입니다. 대신 상단에 눈에 띄는 경고와 `네트워크 복구` / `재연결` 버튼을 띄웁니다.
- **크래시 복구** — 앱 자체가 죽어도 방화벽 상태는 남습니다. 다음 실행 시 기록을 읽어 자동 복구하고 알려줍니다. 인터넷이 안 되는데 이유를 모르는 상황을 막기 위한 장치입니다.
- **DNS** — 터널을 통과하는 이름은 터널 안에서 조회되므로 로컬 네트워크는 무엇을 찾는지 볼 수 없습니다. 직결 도메인만 로컬에서 조회합니다(안 그러면 은행 사이트가 해외 리전으로 풀립니다).
- **IPv6** — 터널이 v4 전용일 때 남은 v6 경로가 터널을 통째로 우회합니다. 기본 차단.
- **서버 호스트명 해석** — 터널이 아직 없을 때 서버 주소를 터널로 풀 수는 없으므로 항상 직결로 해석합니다.

### 모드와 스택

| 선택 | 빠름 | 대신 |
|---|---|---|
| TUN | — | 프록시를 무시하는 앱까지 전부 포착. 드라이버·관리자 권한 필요 |
| 로컬 프록시 | 오버헤드 최소 | 프록시를 인식하는 앱만 보호되고 **나머지는 그대로 샙니다** |
| 스택 `system` | 가장 빠름 | OS 스택에 의존, 일부 환경에서 문제 |
| 스택 `gvisor` | 느림 | 유저스페이스 스택, 호환성 최고 |
| 스택 `mixed` | 중간 (기본) | TCP는 system, UDP는 gvisor |

### Tor

번들된 Tor 0.4.9.11과 lyrebird가 obfs4·webtunnel·snowflake를 처리합니다. **obfs4와 snowflake는 기본 브리지가 내장되어 있어 브리지를 따로 구하지 않아도 바로 동작합니다.** webtunnel은 기본 브리지가 없으므로 bridges.torproject.org에서 받아 입력해야 합니다.

부트스트랩이 100%가 되기 전에는 상태가 "연결됨"이 아니라 진행률로 표시됩니다. 회로가 없는데 연결됐다고 말하면 요청마다 실패하는 것을 사용자가 이해할 수 없기 때문입니다.

## 함께 쓰기

동시에 켜도 충돌하지 않습니다. Veil을 TUN 모드로 켜면 Shard가 볼 패킷은 이미 터널 안으로 들어간 뒤라 사실상 무의미하므로, 보통은 **둘 중 하나만** 쓰는 것이 맞습니다.

- 그냥 막힌 사이트를 쓰고 싶다 → **Shard**
- 사이트에 집 IP를 안 보이고 싶다 → **Veil** (REALITY 또는 상용 VPN)
- 진짜 익명성이 필요하다 → **Veil + Tor**, 그리고 아래를 읽으세요

## 알려진 한계

- **QUIC의 SNI는 읽지 않습니다.** ClientHello가 연결 ID 유래 키로 암호화되어 있어, 복호화하려면 HKDF + AES 헤더 보호 해제 + AES-GCM이 필요합니다. 1차 구현은 QUIC을 통과/차단/디코이 단위로만 다루고, 차단 시 브라우저가 TCP로 폴백해 우회가 걸리는 방식을 기본값으로 씁니다.
- **`BadSum` 디코이는 NIC 체크섬 오프로드에 되돌려질 수 있습니다.** 주소 플래그로 "이미 유효함"을 주장해 대부분 막히지만 환경에 따라 다릅니다. 안 통하면 TTL 방식을 쓰세요.
- **재조립까지 하는 DPI에는 분할이 통하지 않습니다.** 그 단계에서는 Shard가 아니라 Veil이 답입니다.
- **Shard는 익명성을 전혀 제공하지 않습니다.** 목적지가 우리 IP를 그대로 봅니다.

## 익명성에 대한 솔직한 말

기술 구성보다 운용에서 훨씬 많이 뚫립니다. 실제 적발 사례는 거의 다 여기서 나왔습니다.

- 익명 세션에서 **실명 계정 로그인** — 한 번이면 끝
- 카드 결제, KYC를 거친 암호화폐
- 평소 브라우저·기기 그대로 사용 (브라우저 지문은 IP보다 강력한 식별자입니다)
- 익명용과 일상용 세션 혼용
- 항상 같은 시각에만 활동하는 패턴

조사 권한이 동원되는 상황을 상정한 익명성은 개인이 실수 없이 유지하기 매우 어렵습니다. 자체 VPS는 그 상황에서 **보호가 아니라 증거**입니다.
